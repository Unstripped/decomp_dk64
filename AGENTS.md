# AGENTS.md

Matching decompilation of Donkey Kong 64 (USA). Status, ROM map and remaining work: `ROADMAP.md`.

## Hard rules

- **Never commit game data.** No ROMs (`*.z64`, `*.n64`, `*.v64`), extracted binaries (`bin/`, `assets/`), generated asm (`asm/`), or compiler output (`*.o`, `cc -S` `.s` listings; keep experiments in `.scratch/`). All are gitignored or regenerated by `make setup` from the user's own ROM. History was rewritten to remove a ROM and, later, stray root `*.o`/`*.s` compiler output; do not reintroduce either.
- **The build must stay matching.** `tools/dk make` must end with `build/dk64.us.z64: OK` (the global and overlay text/data hashes are checked just before it; any FAILED line stops the build). Never commit a non-matching state.
- Run every build tool inside the container (`tools/dk <cmd>`); the host has no MIPS toolchain.

## Build

```sh
docker compose build                    # builds the dk64-decomp image
# or: docker build -t dk64-decomp .     # direct docker build
tools/dk make setup                    # extract + split (BASEROM=donkey-kong.n64)
tools/dk make                          # build + SHA-1 check
tools/dk make NON_MATCHING=1           # build without hash check into build_nonmatching/ (not compared)
tools/dk make split                    # re-run splat after yaml / symbol changes
tools/dk make progress                 # build, then matched/total function bytes per segment
tools/dk --status                      # dkd server, lock holders, queued requests
tools/dk --stop                        # stop the dkd server (the next tools/dk call starts a new one)
python3 tools/emu/emu.py build         # builds the dk64-emu Docker image (ares-64 + GDB + VNC)
```

The first `tools/dk` call starts a persistent per-checkout container `dk64-<hash>`; it restarts automatically when the image or the `tools/dkd/` server code changes (`DK64_IMAGE` selects another image).

`make split` deletes and regenerates `asm/` and `assets/` (both splat configs); it never overwrites existing `src/*.c`.

## Decompiling a function

Query the IDO knowledge base throughout (mandatory): `python3 tools/quirks.py` searches `knowledge/ido/` (~560 quirks and guides from every past unit), and many problems are already solved there. `func <FUNC>` before writing C; `search --symptom <tag> <words from the diff>` at every stage change and whenever a diff stops shrinking (`tags` maps diff symptoms to tags); `search` before any trick, tool route or derivation you would otherwise work out yourself; `get <ID>` for full text. Record new findings with `add` (main session or orchestrator only; subagents report them).

1. Convert its file to C in the segment's splat config (`dk64.us.yaml`, `dk64.global.us.yaml` or `dk64.<overlay>.us.yaml`: `[0xOFFSET, c, dir/name]`), then `tools/dk make split`.
2. Replace the function's `#pragma GLOBAL_ASM("asm/.../nonmatchings/...")` line with C; `tools/dk python3 tools/m2c.py [-s SEGMENT] FUNC` gives starter C.
3. `tools/dk make`; on mismatch, `tools/dk ./diff.sh [-s SEGMENT] FUNC` shows the asm diff against the original.
4. For non-trivial functions, follow the 6-stage order (from the OoT IDO 5.3 -O2 guide): (1) behaviourally equivalent C (m2c), (2) basic-block order, (3) large reorderings, (4) same callee-saved register set and frame size, (5) small reorderings, (6) register allocation. Always report the stage reached, not only an instruction count; register-allocation tricks are wasted before stage 4.
   - At stages 4–6, diagnose register allocation with `tools/uopt_trace.sh [-l LEVEL] [-s src/<seg>/<file>.c] <file.c> [FUNC]` on a private copy to compare which candidate got which register against target asm before guessing.
   - When registers are right and only the schedule/shape differs (a hoist, a delay-slot fill, an instruction order), run `tools/as1probe.py keep` then `scan` on the private copy first: in about a minute it lists the single ugen-record edits that give the target and says which C could emit each. Aim spelling work at the routes it shows; when every hit is one C cannot emit (a `noop`/`bnext` probe, an `alias` where no register holds a variable address), record the edits in the draft and look for several coordinated changes instead (`scan --rounds`, liveness via `live` hits). A scan covers single edits only: it never proves that no C exists.
   - At stages 5–6, use `tools/permute.py setup/run/best` for near-misses. Permuter mutations are NOT semantics-preserving and its score checks disassembly only (stack only via `--stack-diffs`, which the wrapper always passes), not relocations or data. A result is a search hint: rewrite the idea into readable C that keeps the asm's behaviour; normal gates apply (`fdiff`/`objdiff` OK or TEXT OK, then full ROM `build/dk64.us.z64: OK`). Never paste permuter output unreviewed. Bound shared CPU with an explicit small `-j` (e.g. `-j 2`) and `--seconds`.
   - A function that will not match but whose C is genuinely behaviourally equivalent (remaining diff only regalloc/scheduling/stack layout, thoroughly reviewed) may be parked in `src/` using `#ifdef NON_MATCHING\n<C>\n#else\n#pragma GLOBAL_ASM("asm/...")\n#endif`. `tools/dk make NON_MATCHING=1` builds into `build_nonmatching/` without hash check; `make expected`/`progress` refuse `NON_MATCHING=1`; the default matching build is unchanged and remains the sole gate. Parked functions count as unmatched. If not genuinely equivalent, keep the draft in `drafts/`.
5. Name the function and any discovered symbols in `symbol_addrs.us.txt` (boot/global) or `symbol_addrs.<overlay>.us.txt`.

Compiler notes:
- Game code: IDO 5.3 `-O2 -mips2`. libultra: ultralib's J flags by directory (`os/` `-O1`, `gu/`/`mgu/`/`libc/` `-O3`, `io/` `-O2` with listed `-O1` files, `libc/ll*` `-mips3 -32`); see the libultra block in `Makefile`.
- Rare's audio library (global `0x80732420` on: libaudio heap/bnkf, n_csplayer, n_sndplayer, oscillators) is IDO **7.1** `-g` (unoptimised): files listed in `GLOBAL_G_FILES` in `Makefile` build with `/opt/ido7.1/cc`. At `-g` every local lives in its stack slot (first-declared local highest) and statements compile in source order; `uopt_trace.sh` does not apply. `fdiff.sh`/`permute.py` take the compiler from make.
- `while (cond) {}` compiles to a rotated loop with `beqzl`; the original often uses `do {} while (cond);`.
- asm-processor needs `/opt/asm-processor/prelude.inc` (sets `noreorder`). splat's `nonmatching` macro is disabled because asm-processor miscounts its lines.
- `objdiff.sh` exit 3 with `TEXT OK` is normal once C replaces a `GLOBAL_ASM` baseline: IDO emits relocations in a different order than gas, uses plain constants where splat made absolute symbols (`D_80100000`), and addresses jump tables as `.rodata`+addend. The ROM hash from `tools/dk make` is the gate; re-run `make expected` after a matching build.
- IDO gives every declared local a stack slot in declaration order; unused locals are often needed to reproduce frame sizes.
- Write C from the local asm only; this project does not reuse code from the community DK64 decomp.
- IDO uopt priority-based coloring: uopt assigns registers by priority-based coloring (Chow & Hennessy, TOPLAS 1990): priority is estimated savings of a live range weighted by block frequency and normalised by its length, highest first, with live-range splitting. Because candidates compete globally across the procedure, a change in one loop or basic block can shift register choices in another.

## Conventions

- Unidentified symbols keep splat names (`func_XXXXXXXX`, `D_XXXXXXXX`) until their behaviour is confirmed.
- File splits: follow splat's suggestions, but check data/rodata boundaries against 16-byte alignment and string placement (boot rodata is `0x10F60`, not splat's `0x10F74`).
- Converting a global/overlay file to `c`: give its data range a named asm subsegment (`[0xOFF, data, name]`) and switch to `.data` only once the C defines every object in it (a `.data` subsegment emits no asm, so GLOBAL_ASM-only files fail to link). Its rodata can be `.rodata` right away: splat migrates it into the GLOBAL_ASM function files.
- Fake matches: a construct kept only to steer IDO codegen (dead `if (G) {}` statements, `volatile` locals/reads, no-op arithmetic such as `x ^ 0` or `x & 0`, `do {} while (0)` wrappers) carries a trailing `// FAKE: <what it steers>` comment on its line (a trailing comment keeps line-based scheduling unchanged). Source layout kept only for as1's line-ordered scheduling (a statement on the function's `{` line, two statements joined on one line) carries `// LAYOUT: <what it steers>`. `grep -rn "// FAKE" src` lists the remaining debt; replace them with natural C once types and structs are better understood. Unused `pad` locals that only reproduce a frame size are not tagged.
- Prototypes: a function's declaration comes from its generated header `include/proto/<seg>/<file>.h` (`tools/protos.py gen`; never hand-edit it). A `.c` file keeps its own declaration only together with `#define PROTO_SKIP_<name>`, which skips the shared one; these defines sit directly above the `proto/` includes. A skip kept for codegen is tagged `// FAKE: callee prototype steer` (or `// FAKE: implicit declaration steer` when the file had no declaration); a skip that exists because the shared prototype is unusable here (a type it cannot see, a conflicting local struct) is tagged `// PROTO: <reason>` and is resolved by the types phase, not by codegen work.
- Shared globals: declare a global with the type most of `src/` already uses for it (e.g. `extern Actor *D_807FBB40;`), not `void *` plus a file-local struct view or cast macro. A field the shared struct lacks gets named in that struct's padding at the right offset; casting a genuinely polymorphic member (such as `Actor::unk174`) to a file-local struct is fine.
- Update `ROADMAP.md` checkboxes when a step lands; after a matching build that changes progress, refresh `README.md` with `tools/dk python3 tools/progress.py --readme`.
