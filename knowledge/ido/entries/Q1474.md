Global `0x124780` (VRAM `0x8071FA80`-`0x80721560`, 6,880 bytes) is data inside the global `.text`: a dlabel-only asm subsegment (no `glabel`) between 11BC10's and 126260's text, the 176 effect sprite sheets `gEffectGridAssets` (119370) points at. It is now C without moving a byte: the data-only TU `src/global/124780.c` (176 `EFFECT_GRID_ASSET(n)` objects, then IDO's 8-byte 16-align `.data` pad) with the yaml line `- { start: 0x124780, type: .data, name: 124780, linker_section_order: .text }` (dk64.global.us.yaml:168).

splat 0.50.1 `Segment.get_linker_section_order()` returns the subsegment's `linker_section_order` (default: its own section) and the linker writer groups entries by that order while emitting the input section from `get_linker_section_linksection()` (`.data`), so `build/global.ld` lists `build/src/global/124780.o(.data);` between `11BC10.o(.text)` and `126260.o(.text)` in the single `.global` output section (`SUBALIGN(16)`); the map shows `.data 0x8071fa80 0x1ae0 build/src/global/124780.o`. A `.data`-type subsegment is not a text base segment, so splat adds no auto `.rodata`/`.bss` siblings; the TU must define only `.data`.

Hashes stay identical because `global.text.bin` is `head -c GLOBAL_TEXT_SIZE` of the objcopy'd image: it covers bytes, not ELF sections. Constraints: the slot must start 16-aligned (IDO `.data` alignment) and the TU's `.data` size padded to 16 must end at the next text TU's start. `tools/progress.py` counts the object as C data (map `.data` input sections), raising the data total by 0x1AE0. Use this for any dlabel-only `.text` asm run between C files instead of keeping it asm.
