A `void` function whose last statement is a value-returning call compiles exactly like the non-void function that writes `return f(...)`: the callee's `$v0` is left in place either way. When the function is called through a pointer whose return the caller uses, the `void` spelling is a latent bug (and wrong for ports); spell the real return. Verified by full ROM match (issue #1, 2026-11-23):

- render callbacks: `renderCallbacksDispatch` (90D80) does `glist = func(glist, actor)`, so every `renderCallbacksRegister` target returns `Gfx *` (9DD70 renderSetupSegmentsAndFog, A2F10 renderScaledSprite, menu/3E10 menuInitGfxState, race racer/vehicle/particle/HUD callbacks, 103AB0 playerViewCornerMasksCallback, playerViewDrawCameraShutter).
- cutscene conditions (`gCsCondTable`, value tested): 478F0 csCmdCheckCollectedSufficientItems, csCondWorldHubFlagSet return `u8`.
- collision filters (`CollisionFilterFn`, 7A510 `entryAllowed = filter(...)`): 7AF60 actorCheckPlayerSmallerThanAttacker returns `u8`.
- 103AB0 playerViewCaptureSepiaPhoto's bare `return;` for actor 0xD9 returned assetLoad's pointer through playerViewLoadPresetPhoto: `u16 *playerViewLoadPresetPhoto(void) { return assetLoad(...); }` + `return playerViewLoadPresetPhoto();` matches; `return NULL` adds `move v0,zero`.

Contrast: a predicate that falls off the end with a compare in `$v0` (Q0230, Q0580) still needs the missing return; `void` instead of an unused `s32` return can change codegen (minecart/25F0 minecartSetTargetAheadOfPlayer fails). See Q0812.
