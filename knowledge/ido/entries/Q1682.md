The operand order of a two-term integer add comes from cfe: it emits the load of the operand that needs converting first. With operands of equal width source order holds. csCmdHubWorldItemsAdjust (478F0): with `s32 add`, `frame + add` gives the target's `addu a2,t1,v0` (0x6798) and `add + frame` the other order; with `s8`/`s16`/`u8`/`int` add both orders give `addu a2,v0,t1` (cfe ucode: `lod add len 1` before `lod frame len 4`); with `u32 add` the result is frame-first. So Q1619's `x = a; x += b;` split is only needed when one operand is narrower. Before keeping a copy-then-add operand-order steer, give a narrow partner local its plain width when the target never narrows it (`add` held only 5/0: `li v0,5` 0x6790 / `move v0,zero` 0x6794, no byte load or store, summed into an s32 parameter): the FAKE copy went.
