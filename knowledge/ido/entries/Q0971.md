Seen in `tagBarrelOrbitKongs` (src/global/80150.c, cleanup unit HacktagBarrelOrbitKongs2, 2026-11-15). This extends the Q0554 FIFO model. When no other value is holding any of them, ugen's integer scratch free list works as a strict 10-register round robin from the start of the function, in the order `$14 $15 $24 $25 $8 $9 $10 $11 $12 $13`. Each allocation advances the ring, including allocations for code that as1 deletes later as dead or redundant. That deleted code is gone from the final listing, but it still decides which register a later loop gets, through the number of allocations mod 10. In the target, the loop's `mfc1` lands in `t7` ($15), which requires 30 allocations before the loop. Without the extra expression chain, the count is only 15 and the loop gets `mfc1 t2` ($10) instead (full=33). To fix this kind of mismatch, count the scratch allocations before the loop mod 10, including those as1 throws away. Then add or remove C expression work before the loop until the count lines up, rather than editing the loop itself. This only applies while nothing else is holding scratch registers. Once values stay live, the FIFO order from Q0554 takes over.

**2026-11-18 correction (CleantagBarrelOrbitKongsb c2589075):** File src/global/80150.c, tagBarrelOrbitKongs d45e68/b38837/1cc068/c2023d FIXED. CORRECTS Q0971's method advice and the 17f queue CleantagBarrelOrbitKongs item (see Q0374, Q0441, Q0554): when as1 deletes a narrowing chain it renames the chain's first instruction onto the LAST deleted register, so a visible ring register can stand for a deleted chain's last allocation, and hidden allocations can sit after a visible instruction of the same statement. Q0971's "add C work before the loop" was wrong here: the missing allocations were the loop's own slot-angle normalisation (loop `mfc1 $10` + 5 deleted narrowings -> `mfc1 t7` at 0x77c4; pre-loop count stays 15, not 30).
