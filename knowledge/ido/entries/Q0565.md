Do not infer BSS layout from the order of file-scope definitions placed after function bodies. With IDO 5.3 -O2, a small probe with a function-local static followed by `(void)&c; (void)&b; (void)&a;`, then later definitions `int a, b, c;`, places the static at offset 0 and c/b/a at offsets 4/8/12. The address-only statements emit no runtime instructions but establish symbol order. Real earlier accesses likewise take precedence over later definition order.

55B20 uses four tagged `(void)(...)` comma-expression statements in mapChunksInitFromMapData to order the objects following its function-static count. It owns exactly 0x807F6C20-0x807F70B0 (0x490 bytes): count, grid-plane pointer, chunk count, cell flags pointer, two 20-halfword arrays, clipping state/buffers, matrix pointer, and the 50-byte flag array. Normal alignment accounts for the gaps. The preceding mapChunkAllocLists accesses the chunk count through the active D_807F6C28 linker alias so it does not emit gMapChunkCount before the static. A neighbor-pointer store there changed nine instructions; the scalar alias preserves its original code. Check `nm -n` offsets and the full linked ROM, not just object text. The flag array must be TU-owned for as1 to share one lui across the two peeled stores.
