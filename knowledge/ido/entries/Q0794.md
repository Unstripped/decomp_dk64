Duplicate reads inside one block are CSE'd before candidate selection, so a local whose every def and use is in one basic block never becomes a uopt register candidate and is handled as a ugen temp; only a def or use in another block makes it a candidate. Rewriting such a local in any same-block form changes nothing.

Evidence: camUpdateFollowBlend (global/201B0.c): 61 diff lines with any same-block form. Same unit (camUpdateFollowTargetDistance): a struct-pointer field re-read after a call (`cam->unk0->z` beside a cached `actor`) is a real target load, 60a290 -> ORIG at 0x22e4/0x22f0.

**2026-11-17f correction (CleancamUpdateFollowBlend 8e60fa37):** File src/global/201B0.c, camUpdateFollowBlend 1b5c98 FIXED (dead `dist++` gone: dz/dx locals dropped, `distSq = CAM_SQ(target->z - st->eyeGoalZ) + CAM_SQ(target->x - st->eyeGoalX);` with file-scope `#define CAM_SQ(x) ((x) * (x))`; director: ordinary, one macro for every recomputation). CORRECTS Q0794 ("only a def or use in another block makes a local a candidate"): a local whose def and use sit in one block still becomes a coloured candidate when its stored expression contains memory loads, because uopt refuses to propagate it (`has_ilod`, Q0510); float locals holding the operand differences make the expression load-free, so it is propagated into the scratch ring instead. Supersedes Q1064's dead-use route for this function (Q1064's mechanism still measurably true).
