Extends Q1604 from one split label to a pair: two split labels of one struct field pair can fold together through ONE pointer local that the function did not hold before. In jetpac/4FC0 jetpacActorUpdateFighter and jetpacActorSteerToPlayer, D_8002F054 (= jetpacGame.player.head.y) and D_8002F078 (= .head.boxY2) are read as `player->head.y + player->head.boxY2` through `JetpacPlayerActor *player = &jetpacGame.player` (block scope in Fighter, function scope in SteerToPlayer): RELOC-EQUIV, each label keeps its own lui/%lo with only the addend moving; the same holds for an address argument (`&player->head` into jetpacGetEntityCenterX). The direct `jetpacGame.player.head.*` spelling fails (uopt CSEs it with the function's other jetpacGame base: one lui/addiu plus displacement loads, +1 instruction), and the other symbol of the same object, `jetpacPlayer.player.head.*`, folds either label alone but never both (they then share one base where the target has two lui). Related finding in jetpac/1A60 (Q0687 family): which of the two symbols covering one object a function names is load-bearing per function: jetpacIsSpawnDelay, jetpacUpdateLasers and jetpacSetState need `jetpacPlayer` (fdiff 1 with `jetpacGame`), jetpacPlayerStateUpdate, jetpacInitPlayer, jetpacDrawLasers and jetpacDrawPlayer's flip reads are RELOC-EQUIV either way, and jetpacDrawPlayer's outer state test keeps `jetpacGame` because the target loads state twice (lw 0x1054 via jetpacGame, lw 0x1070 via jetpacPlayer). Ruled ordinary C (R2-27, director 2026-11-27: a pointer local held for use, Q0601, the same house style as `JetpacPlayer *playerData = &jetpacGame.players[...]` in the same function).
