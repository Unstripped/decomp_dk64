This came up in the data carve for the unit "cleanup HackscriptOpPlaySoundAndShake2" (2026-11-15). The initialized global `u8 sScriptChannelIndexTable[4] = {...}` follows the `u8` global `sMotionWindowProgress`, which sits at +0x1DC in .data. IDO 5.3 places the array at +0x1E0, not +0x1DD, and this matches ROM. So when a byte global is followed by a 3-byte gap in ROM data, the gap is alignment padding and not a hidden object. Do not invent a filler symbol for it. The same carve also had a splat label off by 4: splat put `sCharacterBehaviorMap` at 0x80746E10, which is the last word of `sScriptCommandTable`, 4 bytes below the real table. The code indexes the table as `[actorType - 2]`, so the carve's LO16 addend of -4 at 0x4208 resolves to the same address. Moving the label to the real table start only changes relocations, as in Q0264.
