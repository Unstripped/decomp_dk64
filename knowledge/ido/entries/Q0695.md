In `mapNodeAssetParse` the plain `gMapZones[idx]` spelling differs from the target only by an s0/s1 swap between `p` and the slot address. Anything that splits the uopt basic block right after the `p += vertCount * 6 / 2 * 2` advance (in tests, a goto to an adjacent label) matches fully, so the kept `s32 slot` hack is standing in for a block boundary, not for the temp itself.

**2026-11-16b correction (HackmapChunksApplyLights2, merge 94bb42df):** the slot temp was not standing in for a block boundary. The real lever is how often the source updates `p`: an `s16 *p` stream reader with one `*p++` per field (and `p += 16` / `p += 8` after the memcpys) gives `p` enough weight (75.25) to beat the shared `&gMapZones[idx]` address (75.0), so `s0 = p`, `s1 = &gMapZones[idx]` with no hack. A dead guard only worked by lowering the address weight 75 -> 50. The byte-count step `p += (u32)vertCount * 6 / sizeof(s16)` is what produces the target's `srl` then `sll` pair (0x7c20/0x7c24). See also Q0589.
