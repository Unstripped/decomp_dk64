This came from the 2026-11-15 cleanup of hudPauseMenuRender (unit HackhudPauseMenuRender3), going from e1b0a2 to 766e68, which was kept. An addition was spelled `A + (s32)(f)`, and the fix was to write the conversion first as `(s32)(f) + A`. With that order, ugen pulls the `trunc.w.s` scratch register from the ring (Q0583) before it assigns A's register. uopt also swaps the `mul.s` operands that feed the conversion. The affected rows are at 0x131c and 0x1324-0x134c. After the change, full=3. An as1probe scan found no single record that improved the result, so the mismatch in this area was about operand order in C, not about a scheduling record. This is the same kind of effect as the no-op masks in Q0374: how the C is written changes which scratch register ugen takes and when, even when the arithmetic is identical. When a `trunc.w.s`/`mfc1` pair and a nearby integer register have their scratch names swapped, try both operand orders of the commutative add before trying other FAKE changes.
