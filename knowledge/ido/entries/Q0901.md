Scope limit for Q0552, from the HackeepromSaveRecords2 cleanup (ledger c5d9ef70) in 104F0.c. This TU's data `D_807467C0`..`E8` includes the `D_807467D0` dispatch table, whose entries are `eepromSaveRecordsAll` and `eepromSaveRecordsOffset`. Defining all of that data in the same C translation unit did not change any of `eepromSaveRecords`' instructions. Each of the five dead-guard removals scored the same with the data defined and without it. The as1 address-taken effect on XBB block weights (Q0552) seems to need a switch `jr` inside the function being scheduled. EFDC0's `playerStateSetFlagsByActorType`, the second case in Q0552, has such a switch. `eepromSaveRecords` has none, so function-pointer data alone is not a lever there. In that case the dead-guard padding described in Q0548 is still the relevant mechanism. Before adding a missing data table to fix a schedule, check that the target function actually dispatches through a jump table. Unit "2026-11-15: cleanup HackeepromSaveRecords2".
