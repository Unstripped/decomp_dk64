IDO 5.3 emits a TU's initialised .data in definition order and starts every object on a 4-byte boundary (Q0395), so a 2-byte gap after an s16 global is object alignment, not evidence that two globals are one struct. Definitions scattered through the file still emit in source order, so a data-to-C move puts the whole data block, in address order, at the top of the file. Defining a global in the same TU does not change uopt's lda web for it (Q0255, Q0761).

Evidence: global/109660.c (carve `[0x1599E0, .data, 109660]`, 0x80754CE0-0x80754F80, merge 8adf989e): D_80754CE0 +0x0 / D_80754CE4 +0x4; gBgScrollX +0x290 / gBgScrollY +0x294 are two separate s16 globals. gfxBuildScrollingBackground's stores still share lda web {551|1} with the tail read (1c23c5/797f1c re-measured on 17 variants, scores unchanged).
