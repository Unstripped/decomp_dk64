uopt identifies an indirect-load candidate by its base variable and offset only, so every respelling of the same address (a cast to another struct view, a byte offset, `(&field)[k]`) is CSE'd. A store through the same base (an f32 field store) breaks GLOBAL availability of an unrelated s32 field (PRE reinserts the load after it), but a reload in the same extended block after the store is still value-numbered to the earlier load and deleted. A target reload after a store that does not re-establish availability can therefore only come from a non-candidate load: `volatile`, or a different base variable.

Evidence: jetpacUpdatePlayerMovement (jetpac/1A60.c): volatile 1d4065 stays (director rejected moving the volatile into jetpac.h).

Corrected 2026-11-15 (HackjetpacUpdatePlayerMovement2, ledger 66af0754): the candidate key also includes the load dtype. In jetpacUpdatePlayerMovement each `volatile` s32 reload of `player->flying` after the `swc1 12(s0)` vy store can be `*(u32 *)&player->flying`: the u32 load is a separate candidate, is not merged with the s32 else-if test load at 0x9ac, and the object matches. Still a punned-cast hack (tagged), but a third non-candidate route besides `volatile` and a different base variable.
