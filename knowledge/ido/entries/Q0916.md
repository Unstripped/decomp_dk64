In `HackcsCmdExec2` (cleanup unit 2026-11-15, kept candidate e8c5ea), the target uses a3 for the flag local `found`, but the natural spelling allocates it to a2. Adding a dead `if (found) {}` right after `found = 0` at function entry fixes the allocation. The dead guard still counts as a real uopt use (Q0561), so found's live range now covers block 0. There it interferes with the incoming-csId argument candidate {282|1}, which adds a3 to that candidate's forbidden set and changes the colouring order, so found gets a3 (`move a3,zero` at 0x2140 ... `bnezl a3` at 0x38a0). This fits Q0492's rule that the block extent of a live range changes candidate priority. Other spellings did not work: putting the zero in found's initialiser, inverting the test, and changing found's width all stayed 5-6 rows off. The guard only helps when it sits in the entry block, next to the incoming-argument candidate.
