HackcsCondEval2 (unit "2026-11-16b: cleanup HackcsCondEval2", merge 5d61f35b), src/global/42630.c csCondEval (cfe operand order, refines Q0185/Q0711): a named struct field leaf (`cmd->a`) is canonicalised to the left compare/addu operand, an indexed array read (`cond->arg[0]`) keeps source order, giving the target's `bne field,arg` (cases 0x4 at 0x188c, 0x31 at 0x1808); case 0x17 needs the opposite order and keeps a punned named read (3f5f75).

**2026-11-16d extension (HackcsCondEval3, merge e3122cc2):** a value loaded once and reused in a register (tested, then compared) is the RIGHT compare operand when read by plain indexing; an int-width local declared just before the compare (`s32 arg = cond->arg[1]; if (a->unk155 == arg)`) puts it LEFT (`bne a1,t7` at 0x1ec0 in csCondEval case 0x17) in either source order, like a named field leaf. `(s16)` casts and an s16 local do not (54); copying before the `!= 0` test makes it long-lived and reallocates the function (1061). See Q0711, Q0601, Q0474.
