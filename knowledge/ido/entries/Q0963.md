In `enemyAggroStateUpdate` (global/12E800.c, unit "2026-11-15: cleanup HackenemyAggroStateUpdate2", merge 94e24451, record 61bdd789), commits c57b42/5bba72/1ad395/5bba72#2 had marked a `& 0xFF` mask on the 0/1 s32 flag `near` as FAKE. It was reclassified as ORIG. The target emits `andi t,t4,0xff` before every `near` test (0x305c/0x3080, 0x3168, 0x32d8, 0x33f4/0x341c), and the lead confirmed this in the expected .o. Case 0x35 tests the same register plainly (`sltiu t4` / `beqz t4` at 0x34b0/0x34b8) with no mask. No declared width reproduces the mask: plain s32/u32 scores 157, u8/u16 scores 222 and s8/s16 scores 208. So the mask must be written at each test site in the source. The rule: if the target .o shows a per-site mask that changing the variable's type cannot produce, treat the mask as the original source, not as a steer. This extends the evidence rule used in Q0602 and Q0474.

**2026-11-17 application (HackplayerStateWaypointAimUpdate3, merge 5d8f9580):** the target's `andi t4,a1,0x1` on an sltiu result (playerStateWaypointAimUpdate 0x3500/0x3504) is reproduced only by an s32/u32 variable plus a source `& 1` (tagged ORIG); u8/u16 77 lines, s8/s16 80, s32/u32 without the mask 79.
