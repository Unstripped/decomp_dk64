In `raceSteerTowardTargetWaypoint` (src/race/6650.c, unit "2026-11-15: cleanup HackraceSteerTowardTargetWaypoint2", commits 11f5b9/b8545a), two empty guards sit in different blocks: one on `gCurrentActor->x` in the first arm, one on `waypointRadius` after the threshold. Each one alone changes nothing. Together they put steerAngle/angleDelta in `$f18`/`$f16`. Without both guards, steerAngle spills to `100(sp)`. This is another coupled-steer knot like Q0602, so remove or add the guards together. An empty `;` at either position does not reproduce the effect. So unlike Q0698, these guards are not block-split levers. They act as real uopt uses (Q0561). There is also a negative result for the statement-order lever from cannonUpdate (Q0468/Q0739). Once the copy is optimised away, the order of the post-call copy, radius and threshold statements makes no difference here.

**2026-11-15c correction and refinement (dead-guard classifier):** the two guards here are BLOCK SPLITS, not uses. Replacing either guard's operand with an unrelated local (idx, targetSpeed, waypointThreshold[0]) still scores 0, while a guard on distToWaypoint at the second position scores 42 (it adds a use). uopt -l6: the two extra blocks drop dist (cand 59) below steerAngle and dist splits (190/191); without them dist takes $f16 whole and steerAngle cannot be coloured (raceSteerTowardTargetWaypoint, unit "2026-11-15: cleanup HackraceSteerTowardTargetWaypoint3", b5dcafe6). Classify every dead guard by replacing its operand before trying to remove it:

- **Block split.** The guard still works with its operand replaced by `1` or by a local already live in the competing range; the lever is the block count inside the competing candidate's range (supply blocks, not reads). A guard on a local that is NOT live there extends that local's range and can fail even for a real block split (actorBoneChainSwingUpdate: nodeCount 19, p 274), so test with `1` or a live local. Some splits need TWO blocks: test a two-term `&&`/`||` on a live local before concluding "not a block split" (playerTurnByStickX 3617c0: any two-term guard on yaw/turn/delta/gCurrentActor matches; one term, `1` or `delta`, gives 9; the competing local itself, `pad && pad`, gives 9 because its use adds savings). Position: the guard must sit inside the competing candidate's live range, and any region of it works (vehicleUpdateMotion: for waterY, cand 24, `if (vehicle) {}` in the late floor-snap then-arm matches like one in the buoyancy arm); outside it fails (actorBoneChainSwingUpdate: `if (1) {}` scores 0 only between the head test and the store, 144/149 elsewhere). An unused label or `;` adds no block there (vehicleUpdateMotion: 38 = removal; contrast Q0877/Q0698). Natural replacements: a one-case switch or early `continue` (Q0945); an assignment in the last `&&` term (Q1032); or, where a named element pointer `p = &arr[k]` is used around a call, repeated `arr[k].f`, which makes the address its own expression and produces the split for real (collisionBstSortFlatItems, global/6AD90.c, 4fdc1ad7: with pivot_ptr the post-loop code is BB 19-20 and the walker is live in the call block, a3; with arr[high].f the pivot address is uixa{arr}{high*20} live in BB 19/20/21, the tail-recursion block moves 21 -> 22 and the walker takes a0; this also fixes the add order, Q0781; replacing only the write-back scored 48-69).
- **Availability guard.** Only a read of the SAME value works; the unrelated-local test changes nothing (score = removal). The guard makes a load available before a branch so PRE reuses it at the join. It needs a real expression use (an if condition or a store): `(void)x;` and `x;` are dropped by cfe (Q1026 lists which dead statements cfe keeps), and bare `if (*v)` is not equivalent. Evidence: slotQueueStateMoveToTarget (global/FCCD0.c, d5faee90): `if (*v == 0) {}` replaced by `;`, `if (slot == 0) {}` or `if (reached) {}` gives 13 = removal, `if (*v)` 12; the guard makes the ilod `*v` available before the null test, so PRE reuses it and the hoisted `.shown` on the NULL path at the join (0x295c) and reloads only on the non-null arm (0x2950-0x2958).
- **Kill lever.** A dead store that kills store forwarding (Q0499) is neither: an unrelated guard or a goto/label between the store and the use does not reproduce it, and the block splits even break the vertex-load CSE temps (collisionTestActorBoxFloor, 182dc597: 311/321).
- **Coupled class.** One dead read can carry a block-count lever and an availability lever at once. An unrelated guard that scores better than removal but not 0 means a coupled class, not a pure block split (arcadeUpdateBouncingBarrel, ledger 9bed751a: (a) the extra block lowers the adjsave of the long-lived `&D_8004BCD0[entIndex]` candidate 4.842 -> 4.600, turning callee-saved s0 into v1 with call-site spills to its home, and `if (1) {}` reproduces this part; (b) only a same-value read also makes the field's ilod a coloured candidate (a0); the unrelated guard scores 187 against 301 for removal). Repeated reads whose term count matters are a same-value class too (Q1030).
