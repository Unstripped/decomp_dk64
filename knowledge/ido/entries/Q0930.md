In `playerInputReadLaneSteer` (global/E4090.c, PolishglobalE4090, merge 6353947b, ledger 0e2e7dc2, base e1a3636c) IDO 5.3 sets the `mul.s` operand order for the clamped value times its sign from the statement form, not from the order the operands are written. Writing the product as one expression, `clamped * sign * 0.0125f`, always gives `mul.s ...,$f10,$f2`, whichever operand comes first. Copying first and then using a compound assignment, `x = g; x *= sign;`, gives the target `mul.s $f16,$f2,$f10`. If the code accumulates into the phi variable without the copy, the operand order stays the same but `$f2` is reused as the destination. This matches the cfe operand-order family (Q0737, Q0304): `op=` and `a = a op b` emit operands differently. Rule: when no written order of a commutative FP multiply gives the right operand order, try a copy into a fresh local followed by a compound assignment.
