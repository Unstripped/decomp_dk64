uoptinput.c (~1665-1700) forwards a variable load from the preceding assignment in the same block unless the assigned value contains an `ilod` with count 1; then the load stays real (`swc1` then `lwc1`) and the store is kept. Variables whose right-hand side has no indirect load (in `lightApplyToActors`: `dirX = dx / dist`, `aX = dx / dist`) are forwarded, so their stores are dead unless a later read exists; the target's three kept `aX/aY/aZ` stores therefore imply later reads. Also from that function (leftovers revisit 13, not matched): natural C colours `dx/dy/dz` in fs1-fs3 and leaves `dirX/Y/Z` in the stack (their values live in the shared `dx / dist` expression candidates); a read of dx/dy/dz after the loops lowers their priority and flips it to the target (dirX/Y/Z fs3-fs5, dx/dy/dz pieces f0/f2/f14). The no-code form for an f32 dead read is `if ((s32)dx) {}`; `if (dx && dy && dz) {}` leaves `lwc1` + `c.eq.s`, and `(void)x`, `x + y + z;` and an unused copy are dropped by cfe with no effect. The FP ring is f4-f10 plus f16/f18 only while uopt colours nothing there (Q0442); one coloured piece in f16/f18 shrinks it for the whole function.
