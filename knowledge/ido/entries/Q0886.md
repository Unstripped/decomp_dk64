In slotQueueInit (global/FCCD0.c, function 0930b5), the target computes the address with `inv` as the first `addu` operand (`addu t9,s8,t8` at 0x494). Splitting `inv + id*sizeof` into two statements, either with a separate s32 `kongId`/offset local or as `p = inv->kong; p += id`, produces that inv-first `addu`. But it also reserves a 4-byte temp below the named locals, so the frame grows by 8 (target 0x36c). A one-expression form keeps the frame size but reverses the `addu` operands. Only a FAKE two-step that parks the offset in the pointer variable itself gets both the operand order and the frame right. So when operand order and frame size pull against each other in an address computation, try reusing the pointer variable as the scratch for the offset. Evidence: merge 93d95d6b, ledger 41d32f38, base cf3a64b4. Unit "2026-11-15: cleanup HackslotQueueInit2".

**2026-11-15c correction:** the kongInv byte-offset pun and the "two statements grow the frame" constraint were artefacts of the K&R slotQueueGetAddress declaration. With the ANSI u8 callee (Q0925) the natural `&inv->kong[f(i)]` + `slotQueueGetAddress(i)` matches with no FAKE (slotQueueInit, unit "2026-11-15: cleanup HackslotQueueInit3", cf977754); the word at sp+120 is uopt's spill of the `(u8)i` CSE temp (see the Q0808 correction).
