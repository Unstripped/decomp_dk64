In `func_8061F4B0` (global/201B0.c, unit "2026-11-15: cleanup Hackfunc_8061F4B0", merge b6fec7df, record 817bacdc), the draft took a byte-pointer parameter `u8 *zoneFlags` and indexed it as `zoneFlags[i]`. That put the index first in the addu, as Q0813 describes for typed pointers. Getting `addu a1,a0,v0` required the comma-operator steer `(0, zoneFlags)[i]`. The cleaner fix was to give the parameter its real struct type, `CamZoneWeightLinks *links`, and access the data as `links->zones[i]` and `links->weights[i]`, with the caller passing `&e->u.weightLinks`. This produces base-first order with no steer, which extends Q0175's rule that an array member in a struct view emits `addu base, index`. When a flat byte pointer needs a FAKE to get operand order right, check whether the parameter is really a struct whose fields are arrays. Fixing that type, in the prototype and the caller (Q0486), removes the steer.
