loops over the 24-entry `D_807FDCD0` table whose end the original assembled as `%lo(D_807FDD90)` are text-identical with C's `D_807FDCD0+0xC0`: reloc-only, match on the ROM (4 functions pasted).

The reverse (a split splat label rewritten as its parent array) is relocation-only only for isolated reads. Reading `gPlayerPadState[i].heldButtons` instead of the split label `D_807FD63A[i].unk0` next to other reads of the same entry shares one base address across the reads and folds the 0x2A offset into the load, which changes register allocation (`playerInputUpdate`, `playerInputStepLadderClimb`, `playerInputCheckLadderTopOrBottom` keep the labels).

A label at base+offset (`D_80767CC0 == gScheduler+0x280`) is not interchangeable with the base symbol when the original indexes off the base: IDO emits `%lo(base)` plus the offset as a load displacement, different bytes from `%lo(label)+0`. Only when the label's address is folded into the REL addend (`lhu %lo(sym+off)`) is it relocation-equivalent (`playerInputHandleAButtonSub58`, `playerInputCheckLadderTopOrBottom`, `func_806E9070`).
